## Part 1 — Bug fix: CRN simulator hang after switching to Gillespie mode

### Symptom
Running the last cell of `examples/benchmark.ipynb` for the Oregonator at `n = 1000` appeared to hang. The population size is tiny, so it should return almost instantly. It was not deadlocked — simulated time was crawling forward by roughly `1e-4` per second of wall-clock, giving an effective ETA of over half a day.

### Root cause
File: [`src/simulator_crn.rs`](src/simulator_crn.rs), function `gillespie_steps`.

The CRN simulator alternates between two engines: the batching algorithm for large populations, and rebop's exact Gillespie algorithm when few non-passive reactions are expected. The Oregonator at `n = 1000` switches to Gillespie almost immediately.

While in Gillespie mode the *true* configuration lives inside the rebop object. The old `gillespie_steps` advanced rebop but **only wrote back the population delta** (`self.n += delta_n`); it never copied rebop's updated per-species counts back into `self.urn`. So after the first Gillespie round `self.urn` was frozen at the configuration from the moment the simulator entered Gillespie mode.

That stale urn then poisoned the next line's decision. At the top of each `gillespie_steps` call:

```rust
let total_propensity = self.calculate_total_propensity(false);   // reads the STALE self.urn
let time_to_run_gillespie = (1.0 / total_propensity) * self.n.sqrt();
gillespie.advance_until(self.continuous_time + time_to_run_gillespie);
```

The Oregonator has rate constants up to `1.6e9`, so the stale early configuration reports a very large propensity, which makes `time_to_run_gillespie` minuscule. Each call therefore asked rebop to advance the clock by a tiny sliver, and simulated time barely moved. The same stale urn also fed `non_passive_reaction_probability()`, used by the batch/Gillespie switching heuristic in `run`.

The smoking gun: across successive calls the reported config stayed pinned at `[165, 665, 166, 998, 0]` while the simulation was actually progressing inside rebop.

### The fix
Added a helper `sync_urn_from_gillespie` that copies rebop's current counts back into `self.urn` (preserving `K`, zeroing `W`) and recomputes `self.n` / `self.n_including_extra_species`. It is now called at the end of **every** Gillespie round, so propensity calculations and the switching heuristic always see the real configuration.

`finalize_gillespie` (the batch→Gillespie handoff) already did this copy inline, so it was refactored to reuse the same helper — no behavior change there, just deduplication.

### Verification
- The notebook's last cell now finishes in **0.4 s** instead of hanging.
- Raw simulator, before vs. after: `continuous_time` reaches the target `t = 8.0` essentially instantly, and the config correctly evolves (e.g. `X1`/`X3` consumed).
- The Lotka–Volterra trajectory (`n = 10^5`) still runs correctly (~0.7 s).
- New regression test (see Part 2): `test_gillespie_switch_reaches_target_time` drives the Oregonator and asserts the simulator reaches `t_max` within a 15 s wall-clock cap. On a correct build it passes in well under a second; if the sync bug regresses, the test fails fast instead of hanging.

To pick up the fix you must rebuild the Rust extension (see "Rebuilding" below); it has already been built and installed into `.venv` in this working tree.

## Part 2 — `ppsim` / raw-string-species cleanup

The Python package was renamed `ppsim` → `batss`, and the old raw-string / population-protocol API was removed (the current `Simulation` only supports `simulator_method="crn"` with `Specie`-object reactions built via `species(...)` and the `>>` / `|` operators). A lot of pre-rename material was still lying around. This cleanup removes the clearly-dead items and updates the live ones.

Summary: **53 files deleted, 11 files edited, 1 new test file.** All deletions are git-tracked and therefore recoverable via git history.

### Deleted

| Path | Files | Why |
|---|---|---|
| `old_examples/` | 15 | Pre-rename script/notebook graveyard. Every file either `import ppsim` (dead module), references the old `C:/Dropbox/git/ppsim-rust/...pyd` hack, or calls removed APIs (`simulator_method='sequential'/'multibatch'`, `sample_collision_directly`, `write_profile`, the old population-protocol function-rule API). Nothing outside the folder referenced any of it. |
| `examples/crn_data/` | 16 | Old `ppsim`-era output artifacts (pickles + figure PDFs). The pickles embed the dead `ppsim` module, so they can't even be unpickled now. Last touched only in the original "initial commit from ppsim-rust copied files". Unreferenced by any surviving code. |

Also removed the untracked, gitignored `examples/.ipynb_checkpoints/` directory (stale Jupyter checkpoints, including a fully-orphaned `lotka_volterra_testing-checkpoint.py` that carried the dead `ppsim-rust` loader).

- **`examples/dimerization_testing.py`** — removed the same dead `if False:` `ppsim-rust` loader block. **See "Needs your decision" below** — this file is largely superseded and still has cosmetic `ppsim` in internal names.

### Needs your decision — left in place on purpose

These match the "stale `ppsim`" description but deleting/rewriting them is a judgment call I did not want to make unilaterally:

Note that `README.md` (the packaged readme, `pyproject.toml: readme = "README.md"`) is already fully migrated (batss, Lotka–Volterra, zero `ppsim`) and is **no longer generated** from the notebook — the two have diverged. So `README.md` is the current source of truth. **Options for the notebook: (a) delete it (it's superseded), or (b) rewrite its examples to the reaction API.** Complication: its `README_files/` images are shared — `README.md` uses `Lotka_Volterra_Simple.png` and `bibtex.txt` from that folder, so `README_files/` cannot be blanket-deleted.

## Rebuilding

The bug fix is in Rust, so the extension must be rebuilt to take effect (already done in this working tree):

```
maturin develop --release
```

Note: on this machine the release build failed intermittently with a Windows file-lock error (`os error 32`) when writing into the Dropbox-synced `target/` directory. Building with the target dir outside Dropbox worked reliably:

```
CARGO_TARGET_DIR="$LOCALAPPDATA/batss-cargo-target" maturin develop --release
```

## Running the tests

```
python -m unittest tests.batss_tests
```

(There is no `pytest` in `.venv`; the suite is plain `unittest`. It expects `import batss` to resolve, i.e. the extension built above.)

Notable catches: the tracked `.vscode/launch.json` `--package=ppsim` breakage and the two pickled data directories, both of which a plain gitignore-respecting `grep` would have missed. Every deletion was cross-checked to confirm nothing outside the deleted set referenced it.
