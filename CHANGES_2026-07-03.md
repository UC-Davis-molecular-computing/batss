## Part 1 — Bug fix: CRN simulator hang after switching to Gillespie mode

### Symptom
Running the last cell of `examples/benchmark.ipynb` for the Oregonator at `n = 1000` appeared to hang. The population size is tiny, so it should return almost instantly. It was not deadlocked — simulated time was crawling forward by roughly `1e-4` per second of wall-clock, giving an effective ETA of over half a day.

### Root cause
File: [`src/simulator_crn.rs`](src/simulator_crn.rs), functions `gillespie_steps` and `run`.

The CRN simulator alternates between two engines: the batching algorithm for large populations, and rebop's exact Gillespie algorithm when few non-passive reactions are expected. While in Gillespie mode the *true* configuration lives inside the rebop object, not in `self.urn`. The Oregonator at `n = 1000` switches to Gillespie almost immediately and (as we'll see) never switches back.

**The rebop→urn sync code already existed and was correct** — the pre-fix `finalize_gillespie` copied rebop's counts into the urn via `urn.reset_config(&gillespie_config)`. The problem is *when* it runs. The main loop in `run` is:

```rust
while self.continuous_time < t_max && ... {
    if self.do_gillespie {
        if self.just_started_gillespie {
            self.initialize_gillespie_config();   // urn -> rebop, on batch->Gillespie transition only
        }
        self.gillespie_steps(t_max);
    } else {
        if self.just_finished_gillespie {
            self.finalize_gillespie();            // rebop -> urn, on Gillespie->batch transition ONLY
        }
        self.batch_step(t_max);
        ...
    }
    // switching heuristic: sets do_gillespie / just_started / just_finished
}
```

So the only rebop→urn sync point was the *exit* from Gillespie mode. In steady-state Gillespie mode — consecutive `gillespie_steps` calls with `do_gillespie` staying true — nothing updated the urn, which stayed frozen at the configuration from the moment Gillespie mode was entered. (`gillespie_steps` did write back the population-size delta, `self.n += delta_n`, but never the per-species counts.)

The frozen urn is read twice per loop iteration:

1. At the top of `gillespie_steps`, to size the time chunk:

   ```rust
   let total_propensity = self.calculate_total_propensity(false);   // reads the STALE self.urn
   let time_to_run_gillespie = (1.0 / total_propensity) * self.n.sqrt();
   gillespie.advance_until(self.continuous_time + time_to_run_gillespie);
   ```

2. By `non_passive_reaction_probability()` in `run`'s switching heuristic, to decide whether to leave Gillespie mode.

Read (2) is what made the bug self-sustaining. The Oregonator has rate constants up to `1.6e9`; within the first few Gillespie rounds rebop annihilates the fast species and the *true* propensity collapses by ~9 orders of magnitude — but the urn still described the near-initial configuration with its huge propensity. So the heuristic always concluded "stay in Gillespie," `finalize_gillespie` — the one sync point — was never reached, and the urn stayed frozen forever. Meanwhile read (1) kept sizing the time chunk for the stale huge propensity: ~`1.8e-10` time units per iteration, i.e. ~`10^8` loop iterations to reach even the first history checkpoint at `t = 0.016`.

The smoking gun: across successive capped calls the urn config stayed pinned at `[165, 665, 166, 998, 0]` while the simulation was actually progressing inside rebop.

**What the bug was NOT: lost or repeated progress.** `self.gillespie` (the rebop object), `self.continuous_time`, and the mode flags are all persistent struct fields, and `initialize_gillespie_config` re-seeds rebop from the urn only on a batch→Gillespie *transition* (`just_started_gillespie`). So when `run` returned mid-Gillespie-mode, the next `run` call continued exactly where rebop left off — nothing restarted. The capped-call repro shows simulated time accumulating monotonically (`t = 2.9e-4 → 5.9e-4 → 8.8e-4 → ...` across successive 2 s calls). The damage was (a) **pacing** — the microscopic time chunks above, which is the hang — and (b) **observability** — everything that reads the urn during a Gillespie phase saw the frozen configuration, including the Python side's `config` / `add_config`, so history snapshots recorded during Gillespie mode would have been wrong.

### The fix
A granularity change, not new sync logic: the same rebop→urn sync now runs at the end of **every** `gillespie_steps` call instead of only on mode exit. The sync body was extracted from `finalize_gillespie` into a helper `sync_urn_from_gillespie` (copies rebop's counts into `self.urn`, preserving `K` and zeroing `W`), which is why the helper looks nearly identical to the old `finalize_gillespie` code; `finalize_gillespie` now just calls the helper and then `reset_k_count()`, as before.

The helper additionally recomputes `self.n` / `self.n_including_extra_species` from the freshly-synced urn, replacing the old `delta_n` bookkeeping in `gillespie_steps` — which incidentally removes a latent bug there: `new_gillespie_n - original_gillespie_n` underflows u64 whenever the population shrinks during Gillespie mode (it "worked" in release builds only because wrapping arithmetic cancels; a debug build would panic).

### Verification
- The notebook's last cell now finishes in **0.4 s** instead of hanging.
- Raw simulator, before vs. after: `continuous_time` reaches the target `t = 8.0` essentially instantly, and the config correctly evolves (e.g. `X1`/`X3` consumed).
- The Lotka–Volterra trajectory (`n = 10^5`) still runs correctly (~0.7 s).
- New regression test (see Part 2): `test_gillespie_switch_reaches_target_time` drives the Oregonator and asserts the simulator reaches `t_max` within a 15 s wall-clock cap. On a correct build it passes in well under a second; if the sync bug regresses, the test fails fast instead of hanging.

To pick up the fix you must rebuild the Rust extension (see "Rebuilding" below); it has already been built and installed into `.venv` in this working tree.

## Part 2 — `ppsim` / raw-string-species cleanup

The Python package was renamed `ppsim` → `batss`, and the old raw-string / population-protocol API was removed (the current `Simulation` only supports `simulator_method="crn"` with `Specie`-object reactions built via `species(...)` and the `>>` / `|` operators). A lot of pre-rename material was still lying around. This cleanup removes the clearly-dead items and updates the live ones.

Summary: **53 files deleted, 11 files edited, 1 new test file.** All deletions are git-tracked and therefore recoverable via git history.

### Deleted

| Path | Files | Why |
|---|---|---|
| `old_examples/` | 15 | Pre-rename script/notebook graveyard. Every file either `import ppsim` (dead module), references the old `C:/Dropbox/git/ppsim-rust/...pyd` hack, or calls removed APIs (`simulator_method='sequential'/'multibatch'`, `sample_collision_directly`, `write_profile`, the old population-protocol function-rule API). Nothing outside the folder referenced any of it. |
| `examples/crn_data/` | 16 | Old `ppsim`-era output artifacts (pickles + figure PDFs). The pickles embed the dead `ppsim` module, so they can't even be unpickled now. Last touched only in the original "initial commit from ppsim-rust copied files". Unreferenced by any surviving code. |

Also removed the untracked, gitignored `examples/.ipynb_checkpoints/` directory (stale Jupyter checkpoints, including a fully-orphaned `lotka_volterra_testing-checkpoint.py` that carried the dead `ppsim-rust` loader).

## Rebuilding

The bug fix is in Rust, so the extension must be rebuilt to take effect (already done in this working tree):

```
maturin develop --release
```

Note: on this machine the release build failed intermittently with a Windows file-lock error (`os error 32`) when writing into the Dropbox-synced `target/` directory. Building with the target dir outside Dropbox worked reliably:

```
CARGO_TARGET_DIR="$LOCALAPPDATA/batss-cargo-target" maturin develop --release
```

## Running the tests

```
python -m unittest tests.batss_tests
```

(There is no `pytest` in `.venv`; the suite is plain `unittest`. It expects `import batss` to resolve, i.e. the extension built above.)

Notable catches: the tracked `.vscode/launch.json` `--package=ppsim` breakage and the two pickled data directories, both of which a plain gitignore-respecting `grep` would have missed. Every deletion was cross-checked to confirm nothing outside the deleted set referenced it.
